### Real bug caught while verifying: stale cache masked the new product
Ran the script, then queried `GET /api/products?gender=Men` and got `count: 0` even though a direct Mongoose query confirmed the document existed with the right `isActive`/`gender`/`totalStock`. Root cause: the script writes via `Product.create()` directly, bypassing `createProduct`'s controller-level `invalidateProductCaches()` call (which only fires on `res.on('finish')` for real HTTP requests) - so the Redis-cached "0 results" response from earlier testing was still being served under the unchanged cache-version key. Manually bumping the version (`bumpCacheVersion('products')`) fixed it - worth noting for future one-off DB scripts that write Products directly: they need a manual cache-version bump afterward, or a live server won't see the new data until the 300s TTL naturally expires. Also caught a subtlety in `bumpCacheVersion` itself: `getCacheVersion` defaults to `'1'` when the Redis key doesn't exist yet, and `INCR` on a still-nonexistent key sets it to `1` too - so a *single* bump on a fresh install is a no-op (same resulting version string); it took a second bump to actually change the effective cache key. Not a code bug worth fixing (the version key becomes real and increments normally forever after), just a one-time gotcha when bumping cache manually against a database that's never had a real product write go through the controller.
